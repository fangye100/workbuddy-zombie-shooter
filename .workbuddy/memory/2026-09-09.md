## 调查：AI 生成的关卡数据能否被 Game Editor 打开预览

结论：**能打开，但只有静态布局预览**。证据链（只读调查，未改代码）：

- 通路通的，不用改编辑器：`aether.project.json` 的 `scenes[]` + `startIndex`
  → `scene-boot.ts:resolveStartScenePath()` → `renderer.loadScene()`
  → 走 `asset-util.ts` 的 `/__fs/file?path=`（绕开 vite SPA fallback）。
  生成 `.scene.json` + 登记进 project 即可被加载。
- 🔴 `packages/scene/src/instantiate.ts:137` —— `instantiateScene` 只处理
  `MeshRenderer`，**其余组件（SpawnPoint / RoomVolume / NavZone / Collider /
  Script / Light / Camera）一律 push 进 `skipped`**。
  → 纯语义节点在编辑器里零像素。破解法：语义节点**同时挂一个 MeshRenderer 当
  gizmo**（房间=半透明 box、刷怪点=细圆柱），数据仍是语义组件。Unity 同一思路。
- 🔴 `MAX_OBJECTS=64`（packages/render/src/frame-uniforms.ts）→ `applySpecs`
  超了直接 `throw`，catch 后**整体回退 buildDefaultSpecs**（renderer.ts:808-815）。
  表现是"我生成的关卡没出现，变回默认场景"，不是报错也不是截断。
  → 一整关（3 层 × 8 房 + 30 刷怪点）装不下，必须**一房一场景**拆分。
- 🔴 **Play 模式不存在**：全仓 grep `playMode|PlayMode|enterPlay|isPlaying` 零命中，
  S3 未做。→ 刷怪/波次/AI 写了也跑不起来，只有静态预览。
- S2（保存/Inspector）未完成 → 编辑器里改了存不回去，所以**生成脚本必须可重复
  运行**（源设计 → 生成场景），不能靠人工在编辑器里微调。

### 决策建议（已向用户给出）
走 editor 兼容路线，分两层：关卡**布局数据** → `.scene.json`（可预览）；
关卡**逻辑**（波次调度/AI/掉落）仍要写代码，等 S3。
不走"自己生成可执行代码独立运行"——违反 ADR-010（场景是唯一数据载体），
等于再造一套不可持久化状态。

## 实施：一层一关的 Act1 三层关卡（f624112，已 push）

- **粒度拍板**：一层 = 一个 .scene.json = 一关。GDD §4.1 每层只有 2-3 房，
  渲染物件 18/64，预算充足，**之前"8 房爆 64"的担忧不成立**（那是假设错房间数）。
- 新工具：`tools/level/gen-level.mjs`（设计表→场景，幂等；`--start=floor-2` 切启动层）
  + `tools/level/verify-level.mjs`（headed Chrome+CDP 真机验证：boot 日志+页面探针+截图）。
- 新门禁：`packages/scene/test/level-scenes.test.ts`（16 条）——实例化非空、≤64、
  **RoomVolume/SpawnPoint 必须挂 MeshRenderer gizmo**（NavZone 故意豁免：烘焙作用域，无半透明材质画出来挡地板）。
  首跑就抓到 NavZone 隐形 → 修的是断言口径而非数据。
- **编辑器 S1→S2 断层修复（apps/editor）**：
  ① boot 日志说加载成功但画面/Hierarchy 还是 fallback 12 对象——根因有二：
  `loadScene` 后从不调 `panel.refreshHierarchy()`（面板是构造期陈旧快照）；
  `editorCamera` 全仓零消费（相机停 DEFAULT_VIEW distance 9 → 76m 关卡只见局部特写）。
  ② 修法：SceneLoadResult 带回 editorCamera，main.ts boot 应用到 camera+params.cameraElevation，
  boot 后补 refreshHierarchy；ZOOM_MAX 40→120、PAN_LIMIT_XZ 20→120（关卡跨度需要）。
  ③ 教训：**boot 日志可信度有限，DOM/运行时探针才是铁证**——verify 脚本的
  Runtime.evaluate 页面内探针（读 project.json fetch + body innerText）是定位关键。
- 验证结果：boot 18 物体、Hierarchy 17 对象（18-1 background）、画面三房两走廊
  绿/米地板 + 红刷怪点圆柱 + 黑掩体全可见。门禁：typecheck / 458 tests / editor:build /
  scene:check / verify:prefix 全绿。
- 材质教训落地：gizmo 颜色只能用共享材质 s0-s6（override 的 patch 被 resolveMaterialId 丢弃），
  颜色语义化等 S2 override 生效后再做。
