## 🔴🔴 需求澄清（用户原话，推翻我上一轮的"热重载"设计）

用户澄清「runtime play」是**口误**，真实诉求是：

> 在 Game Editor 里点场景 → 点 Play → 让用户在编辑器里跑起来看。
> **不是**「runtime 中改代码实时生效」；**一旦改代码，只能在下一次 runtime reload 生效。**

### 这消除了我识别的"架构冲突"
- 我之前判定「ADR-017『Play 中禁用热重载』vs 用户要实时」为真冲突，并设计了
  方案 A(整轮重建)/B(代次隔离)/C(数据化行为) + L1/L2/L3 实时分级。
- **全部作废**。ADR-017 原约定**本来就对，不需要改**。
- 教训：用户说"实时"时先确认是「运行时热更」还是「点一下就能跑」，别自行升级需求。

### 好消息：用户要的语义，架构已有一半
- runtime 已有 **`runId` 代次机制**（复审 #6：每次构造/reset 递增 runId，
  三代同检，旧 runId 引用一律拒绝）。
- ⇒「改代码 → 下次 reload 生效」= Stop → 重跑 → 新 runId，**天然支持**，不用新建机制。

### 真正要补的：行为代次（behavior epoch）与装载期快照
- Play 启动时**冻结行为注册表快照**，Play 期间行为代码不可变
- 行为代次与 runId 对齐（一代 Play = 一个封闭 epoch）
- 旧代次的选中/Inspector/诊断引用全部失效并**显式告知**（不能静默）

### ADR-018 三条红线（保护 Agent 能力，防编辑器特供）
- **R1 三问检验**：docs/17 §3.2 第 2 问「关闭编辑器还需要吗」必须答「需要」，
  否则是编辑器特供，会把游戏锁死在编辑器里，Agent 写的东西也出不去。
- **R2 行为是内容层**：`assets/behaviors/*.ts` 属「当前游戏规则」层，Agent 自由写不受 UI 限；
  `BehaviorDef.params` schema 反向暴露 GUI —— **schema 即 Agent 与人类的契约面**。
- **R3 执行器注入**：runtime 不 import 行为代码（浏览器 `import.meta.glob` 收集 / CLI 注入 mock），
  保住纯 CPU headless + parity。

### 一次 Play = 一个封闭行为代次
装载期**冻结行为快照**，与既有 `runId` 对齐（复用不新建）。
🔴 跨代必须**显式告知**：代码改了但没重跑 → 编辑器要提示「当前跑的是旧一版行为」，
不能静默（否则是"看起来在跑其实跑的不是你刚改的"，docs/19 最忌讳的假象类别）。
