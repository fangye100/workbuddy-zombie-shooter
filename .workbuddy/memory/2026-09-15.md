## 诊断：关卡里的占位体为什么换不成真 NPC（三个缺口）

用户反馈「场景关卡里全都是 Proxi，怎么换成真正的 NPC」。调查结论：

- ✅ **模型是现成的**：assets/characters/models/ 下 E-01~E-05、B-01~B-03 齐全，
  每角色有 `rigged/*_rigged_animated.glb`（骨骼+动画，最适合 NPC）与 `textured/*_baked.glb`。
- ❌ **缺口 1：characterId → GLB 路径的映射不存在**。roster.json 有完整数值
  （hp/speed/attack/ai/silhouette…）但**没有 model 字段**；packages/content/src/generated/
  里也没有任何 glb 引用。
- ❌ **缺口 2：场景加载不支持 GLB 引用** —— `apps/editor/src/renderer.ts:803-806`
  对 `o.mesh === null`（asset 类型）直接 `continue` 并 warning
  「外部资产网格暂不支持在场景加载期同步取用，已跳过」。
  即：**就算在 .scene.json 里写了 GLB 路径也渲染不出来**。
- ❌ **缺口 3：prefab(S5) 与 Play/Spawn(S3) 都没做** → 「会动的 NPC」当前不可能。
- 背景：关卡里的方块/圆柱是 9/9 生成的 **gizmo 占位体**（instantiate 只认 MeshRenderer，
  语义节点必须挂几何代理才可见），不是错误数据。
- 最小可行路径：让 loadScene 异步加载 asset 网格（编辑器已有 parseGlb）+ 建 characterId→GLB
  映射（正路是 roster.json 加 model 字段走 content:gen；快路径是先在 gen-level.mjs 建映射表）。
  换完仍是**静态模型**，不会动；动起来要等 S3。
- 容量无风险：物件数不变（圆柱换模型仍是 18/64），只涨三角形（E-01 900 tris × 6）。

### 🔴 踩坑 1：WGSL bind group visibility — tsc / vite build / 单元测试全都拦不住

第一版把 `toon` 的 visibility 只给 `GPUShaderStage.FRAGMENT`，但 `vs_outline` 要读
`toon.outline` 算描边宽度 → 运行时 `CreateRenderPipeline` 抛
`Entry point's stage (ShaderStage::Vertex) is not in the binding visibility`，编辑器进 fatal 页。

**三个门禁全绿（typecheck 0 error / vite build 0 warning / 500 测试通过），只有实机抓得到。**
修法：`visibility: GPUShaderStage.VERTEX | GPUShaderStage.FRAGMENT`。
→ **铁律：每新增一个 render pipeline 或 shader entry，必须实机跑一次**（headed + 真实 GPU）。

### 关键实现决定

- 动态实例**不碰 `transformBuf`**：它的大小（64 × 256B）就是 `MAX_OBJECTS` 的根因，
  shader 侧 `scene.wgsl` 的 `transform` 还是**单个** uniform 不是数组。新开 storage buffer 即绕开。
- 画在 **pass 1 的同一 MRT + depth 上**（`pass.end()` 之前），因此自动参与 toon / 雾 /
  描边 / 全部后处理，与静态关卡同一束光。
- **按体型分组 batch**（`meshId = capsule:r0.340:h1.750`），网格按 (radius,height) 生成并
  缓存在 core（ADR-001）。draw call = 体型种类数（≤9），远好于 500。
- 选中 = 实例色 ×1.9，**不引入第二套高亮管线**。
- 全仓此前 **instancing 完全不存在**（8 处 drawIndexed 的 instanceCount 全是 1，
  无 drawIndexedIndirect，VAT 只有枚举没消费者）—— 这是第一条。

### 🔴 顺带修掉的运行时缺陷：刷怪点共用一条 RNG 流

- 症状：改 A 的 `count` 会把 B、C 的**初始散布整体平移**（多消耗几个随机数就把后面的
  取点推走了）。作者以为在做局部编辑，实际整关重排。

  `changedNodeIds == [target]` 在改 **count** 时挂掉才暴露 —— 改 radius 不挂（不改变取数个数）。

### 🔴 本轮最值钱的教训：固定调试端口会接管上一轮残留 Chrome 的旧页面

- 症状：同一份探针，跑一次全绿、再跑一次 §8-1 报「输入指纹不等」（差异恰好一处
  `nodes.7.components.0.radius: 4.75 vs 1.5`）、§8-5 报「画面里没有可见实体」（`eye=[0,0,0]`、投影 y 恒为 77.9）。
- 迷惑点：磁盘干净、dev server 用原生 https.get 取到 1.5、`/__fs/file` 确实发了 `no-cache`——
  **所有服务端证据都说 1.5**，只有「页面启动时」看到 4.75。
- 根因：探针用**固定**调试端口 9336 且结束后不等 Chrome 退干净 → 本轮连上上一轮实例，
  旧页面带着上一轮「保存后」的内存文档被当成本轮页面。
- 修法三条缺一不可：① 端口每轮唯一 `9300 + pid%600`；② 接管前用 `performance.now()`
  验页面年龄（>30s 判陈旧，改 `Target.createTarget` 新开 tab）；③ 结束 `await` 进程真的 exit，
  外加 `Network.setCacheDisabled`。
- 通用结论：**验证脚本的「被测对象身份」本身就是一条隐含断言。** 端口固定 + 不复验页面年龄，
  会让全部断言一起说谎，且症状与真实缺陷无法区分。
- 修好后：**21 PASS / 0 FAIL，连续三次一致**。

### 诚实结论：删 `screenRay()` 不是修 bug

- `main.ts` 原本另有一份手算 lookAt 基向量的 `screenRay()`；本轮删掉，统一走
  `renderer.pointerRay()`（对 `core.invViewProj` 反投影，与画这一帧的 `viewProj` 严格互逆）。
- 我把**旧公式原样复刻**回探针打同一枪做对照 —— **它也命中**。
  所以正确描述是「消除重复实现（单一真源）」，**不是**「修复了拾取错位」。
- 教训：报告里的「我修好了 X」必须由对照实验支撑，不能由「我删了它」充当证据。
