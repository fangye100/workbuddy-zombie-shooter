## 1. M4 到底要交付什么

docs/20 的原始定义：

> **M4** | 规模与降级：200 只压测、LOD / 远处退回胶囊、mobile 档位（16 帧 / 1 clip） | 帧率与显存记录

三件事，缺一不可：① 真跑 200 只并留下数字；② 远处真的退回胶囊（不是只把字段写对）；
③ mobile 档位真的接进烘焙。

**交付前的状态**：`updateLod` / `selectLodTier` 早在 character.ts 里写好了，但
**全仓库零调用**；`bakePosePalette` 也从不传 `fps`。也就是说 M1~M3 建好的降级能力
一直是"零件在仓库里、没装上车"。

## 2. 实现

### 2.1 LOD 接线（远处退胶囊）

| 位置 | 改动 |
|---|---|
| `packages/runtime/src/session.ts` | `DEFAULT_LOD_THRESHOLDS`（Full 25m / Vat 60m / 迟滞 10%）；`refreshLod(camX, camZ)`；`EntityView.lodTier` |
| `apps/editor/src/services/runtime-bridge.ts` | 批次按 `lodTier` 分流：Proxy 落胶囊批次（key 按**体型**而非 characterId，同体型不涨 draw call）；`refreshLod()` 转发 |
| `apps/editor/src/main.ts` | Play 循环每帧按编辑器相机眼位刷新，**必须在 `batches()` 之前** |

两个实现期的坑（都留下了注释）：

- 🔴 **LOD 必须显式启用**。`CharacterTable.alloc` 把 `lodTier` 初始化成 `Proxy(2)`
  （语义 = 尚未定档）。若不看开关就分流，所有实体一上来就退胶囊，真模型批次的断言
  全废 —— 接线时实测踩到 7 条测试变红。现在 `refreshLod()` 被调用即视为启用，
  未启用的宿主（Node 测试、无相机回路）保持旧行为。
- 🔴 **LOD 是渐进升级的**（Proxy → Vat → Full，一帧只跨一档）。单帧刷新只能从
  Proxy 升到 Vat —— 压测断言"近处真模型"要跑两帧以上才成立，否则会误判降级没生效。

### 2.2 mobile 烘焙档

新增 `packages/render/src/quality.ts`（纯数据 + 纯函数，10 条单测）：

| 档位 | fps | 片段上限 |
|---|---|---|
| t0 | 16 | 1 |
| **t1（本项目 `render.targetTier`）** | **16** | **2** |
| t2 / t3 | 24（= `PALETTE_SAMPLE_FPS`） | 不限 |

档位真源是项目文件的 `render.targetTier`，由编辑器启动时读入并**先于任何 preload**
设置（`ActorLibrary.setBakeProfile`）—— 已装配的角色不会因改档位重烘，重烘会让
`paletteBase` 布局与已发放的 `ActorMesh` 引用脱节。

裁剪用 `limitClips()`：取前 N 个（顺序稳定），`null` 表示不裁剪。

### 2.3 压测通道

`RuntimeSession.debugSpawn(characterId, x, z, count, spreadM)` —— 明确的**调试通道**：

- 走与玩法相同的槽位初始化（`initNpcSlot`，与 `spawnBatch` 共用，血量等真源一致）
- 🔴 `sourceOf = null`：不计入任何房间存活数，**不影响 WaveScheduler 的清空与推进**
  （有测试守着：只清玩法刷出的那批，房间就必须判定清空、wave2 必须投放）
- 容量用尽时返回实际生成数，不抛

压测探针 `tools/verify/stress-probe.mjs`：注入近场 + 远场两组、采样 10 帧、
读批次构成与 JS heap、**数字落盘** `.workbuddy/tmp/stress-report.json`（不靠人从控制台抄）。

## 3. 实测数字（2026-10-02 · 本机 NVIDIA + headed Chrome WebGPU）

| 指标 | 基线（8 只） | 压测（208 只） |
|---|---|---|
| 帧率 p50 | 60.0 fps | **60.0 fps**（min 59.98 / max 60.04，10 样本） |
| draw calls | 35 | **37** |
| `stats.triangles` | 2324 | 2324 |
| JS heap used | — | 44.7 MB / 上限 4.4 GB |
| LOD 分布 | — | **Full 108 · Proxy 100** |
| 批次 meshId | capsule(玩家) + actor:E-01/E-02 | 同左 **+ capsule:r0.340:h1.750**（E-01 的胶囊档） |
| console error | 0 | **0** |

**怎么读这组数字**

- 208 只只比 8 只多 **2 个 draw call** —— 这是 instancing + 按体型分档的应有表现；
- 帧率维持 60fps：**60 是 vsync 上限**，只能说明"本机桌面 GPU 下 208 只不构成瓶颈"，
  不能当作 mobile 的结论；
- `stats.triangles` 在两档下相同，说明该统计**只覆盖静态通道**，不含动态实例批次 ——
  所以三角形数不是规模指标，别拿它做回归断言（已在探针注释里标明）；
- 真正的 mobile 数字要上设备测：本机是桌面 GPU，而 mobile 档（16fps / 2 clip）已经
  接线生效（`bakeProfile` 读数 = `{fps:16, maxClips:2}`，来自项目 `targetTier=t1`）。

**明确的局限（不粉饰）**

1. 只测了 200 只 E-01 单一角色；混合编队与 Boss（E-05/E-06 超参）未压测
2. 没有关掉 LOD 的对照数字（本机满帧，对照看不出差异）
3. 显存只取到 JS heap，GPU buffer/texture 占用未统计（WebGPU 无统一查询接口）
4. mobile 真机验证未做
