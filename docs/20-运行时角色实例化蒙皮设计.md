# 20 · 运行时角色实例化蒙皮设计（GPU Skinning + Instancing）

> 目标：把 runtime 里的代理胶囊换成**真角色低模**（8 个已就绪的 rigged GLB），
> 且**一次 draw 上百只**都带动画 —— 用户 2026-09-16 拍板的方向。
> 前置事实：`docs/18` §5（动态实例通道）、`docs/19`（最终报告）。

## 1. 现状与约束

| 项 | 现状 |
|---|---|
| 动态通道 | `dynamic.wgsl` + `drawDynamicBatches()`，实例 12 float（posYaw/scale/color），一次 drawIndexed 画 N 只 |
| 顶点布局 | 只接 location 0/1/2（position / normal / smoothNormal），**不接蒙皮 slot** |
| 蒙皮能力 | **`packages/render/src/skin.ts` 已有完整 CPU 求值**：`evalJointMatrices(state, out)` 输出 `(joints+1)×16` 列主序；`SkinState` 支持 clip / time / speed / loop |
| 静态通道 | 已支持蒙皮（skinBuffer + scene.wgsl binding 7），但受 `MAX_OBJECTS=64` 限制，装不下 500 只 |
| 骨架规模 | 22 根参与蒙皮（+5 tip 槽位 = 27，见 ADR 索引对齐铁律） |
| 硬约束 | 动态实体**一个静态槽位都不能占**；每帧 CPU 不能重算上百只的骨骼矩阵 |

## 2. 方案：烘焙姿态调色板（Baked Pose Palette）

**核心：动画是确定性的循环片段 → 姿态矩阵可以在加载时一次性烘焙，运行期零 CPU 重算。**

```
角色 GLB（已 rigged + animated）
  → 对每个 clip 按固定采样率（默认 24 fps）逐帧 evalJointMatrices
  → 拼成 palette: Float32Array[ poseCount × jointCount × 16 ]
  → 上传 storage buffer（binding 4），整场不变
实例只带一个 poseIndex（由 tick 推出），shader 直接索引调色板
```

- **CPU 成本**：只在加载时跑一次（8 角色 × 2~3 clip × 24 帧 ≈ 400~600 次求值，毫秒级）。
- **每帧成本**：只上传实例数组（16 float/只），骨骼矩阵不再动。
- **显存**：`8 角色 × 3 clip × 24 帧 × 22 关节 × 16 float × 4B ≈ 810 KB`；
  mobile 可降到 16 帧 / 只烘 1~2 个 clip → ~180 KB。
- **draw call**：每个 characterId（含 LOD）1 次；8 个角色 = 8 次，与实体数无关。

### 为什么不用「每帧 CPU 重算 + 大 buffer」

500 只 × 22 关节 × 16 float = 176k float = 704 KB/帧上传，且每帧 500 次 `evalJointMatrices`
（每次 ~27 次矩阵乘）—— mobile 上必然掉帧。调色板把这块成本搬到加载期。

### 为什么不用顶点动画纹理（VAT）

VAT 要重烘顶点、体积大（顶点数 × 帧数 × 3），且换 clip 要换纹理；
调色板复用现成的 `evalJointMatrices`，骨骼数远小于顶点数，且 clip 切换只是改索引偏移。

## 3. 数据布局

### 3.1 实例数组（12 → 16 float，64 B）

```
[0..3]   posX, posY, posZ, yaw
[4..7]   scaleX, scaleY, scaleZ, paletteBase（调色板内该角色的起始 pose 下标）
[8..11]  albedoR, albedoG, albedoB, poseIndex（本帧姿态下标，相对 paletteBase）
[12..15] clipFrameCount, phase01, flags, (pad)
```

- `paletteBase` 放实例里而不是 uniform：**一次 draw 只画一个 characterId，但所有批次共用同一 bind group**
  （现状就是每批次把 instances 写到 offset 0），放实例里最省事且天然正确。
- `flags` bit0 = 是否蒙皮（0 = 胶囊代理，1 = 真模型），保证**没有加载到的角色自动退回胶囊**。

### 3.2 调色板 buffer（binding 4，`array<mat4x4f>`）

- 布局：`[pose][joint]` 行主展开，`index = (paletteBase + poseIndex) * jointCount + joint`
- 末尾恒等关节保留（未蒙皮 primitive 绑到它），与 `skin.ts` 现有约定一致

### 3.3 顶点：加蒙皮 slot

动态管线在角色批次上额外绑两个顶点缓冲：

- location 3：`joints` — `vec4<u32>`（或 `vec4<f32>` 兼容现有关卡）
- location 4：`weights` — `vec4<f32>`

`dynamicMesh(meshId)` 的缓存从 `{vbuf, ibuf, indexCount}` 扩到加可选的 `{jbuf, wbuf}`，
仍由 core 持有并随 `clearDynamicMeshes()` 释放（ADR-001：GPU 资源归 core）。

## 4. Shader 改动（`dynamic.wgsl`）

```wgsl
@group(0) @binding(4) var<storage, read> palette : array<mat4x4f>;

fn skinPos(i : DInst, p : vec3f, joints : vec4<u32>, w : vec4<f32>) -> vec3f {
  if ((i.flags & 1u) == 0u) { return p; }          // 未蒙皮：胶囊代理走老路
  let base = u32(i.paletteBase) + u32(i.poseIndex);
  let jc = u32(i.clipFrameCount);                   // 复用：关节数另走 uniform 更干净，见下
  var acc = vec3f(0.0);
  for (var k = 0u; k < 4u; k = k + 1u) {
    let wi = w[k];
    if (wi <= 0.0) { continue; }
    let m = palette[base * JOINT_COUNT + joints[k]];
    acc = acc + wi * (m * vec4f(p, 1.0)).xyz;
  }
  return acc;
}
```

- 关节数 `JOINT_COUNT` 用编译期常量（22），与 `_tools/humanik_skeleton.json` 同源；
  将来变骨架要改三处（同 ADR 索引对齐铁律的处理方式）。
- `vs_main` / `vs_outline` 都要先 skin 再 `place()`（外扩用 smoothNormal，且 smoothNormal 也要过蒙皮）。
- **不插值**：先取最近帧（24 fps 采样）。脚部滑行若明显，再做相邻两帧 lerp（双倍取样开销，列为后续项）。

## 5. 装配与生命周期

- 新增 `apps/editor/src/services/runtime-actors.ts`（**编辑器侧**，不进 `packages/runtime` ——
  runtime 必须保持纯 CPU、不认 GPU 资源，见 docs/17 §3.5 单一 owner）：
  - `loadActor(characterId)`：按需加载 `assets/characters/models/<ID>/rigged/*_rigged_animated.glb`
  - 烘焙调色板（复用 `evalJointMatrices` + `seek()`），得到 `{ mesh, palette, jointCount, clipMeta }`
  - `actorBatch(characterId)`：给 Bridge 用的网格 + 调色板偏移
- `RuntimeBridge` 批次：meshId 从 `capsule:r:h` 换成 `actor:<characterId>`；
  **角色未加载成功 → 保持胶囊**（不能因为缺资产就让运行世界少东西）。
- Play 开始装配 actor，Stop 时 `clearDynamicMeshes()` + 释放调色板 buffer（现在已有登记表的机制可复用）。
- 动画相位 = `f(tick)`：确定性，Node 与浏览器一致（虽然 Node 不渲染，但同一套输入可断言 poseIndex）。

## 6. 落地分期

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M1** | 纯 CPU：加载 rigged GLB + 烘焙调色板，单测断言 bind pose 帧 = 单位阵、走跑两帧不同、表面积保持 | vitest |
| **M2** | 渲染：调色板 buffer + 实例 16 float + shader 蒙皮；**先只挂 1 个角色、关掉动画**（固定 bind pose） | 浏览器里看到真模型而非胶囊 |
| **M3** | 开动画（按 tick 取帧）+ 全部 8 个角色 + 未加载退回胶囊 | 浏览器 + `verify:parity-host` 不回归 |
| **M4** | 规模与降级：200 只压测、LOD / 远处退回胶囊、mobile 档位（16 帧 / 1 clip） | 帧率与显存记录 |

## 7. 风险与未决

- **骨骼归一化 T**：`skin.ts` 的 `normalization` 是 per-skeleton 的，调色板烘焙必须用同一套 T，
  否则真模型会整体偏移/缩放（与静态通道的表现要逐位对齐）。
- **tip 骨**：27 槽位里 22 根参与蒙皮，烘焙时按 `joints.length` 走，不要带 tip（tip 权重恒 0）。
- **动画帧与移动速度不同步**：走跑速度与动画帧率是两套量，滑步问题归 docs/16（Motion Match / IK），
  不在本轮解决；本轮只保证"有动画且在动"。
- **未决**：`flags` 塞在实例里会让 12→16 float 的改动波及所有现有批次；也可以改用
  「胶囊批次与角色批次走两条 pipeline」避开。M2 前定，倾向前者（代码路径少一半）。
