# 18 · 运行时责任收敛与取舍记录（WU-0）

对应 `docs/17` 的第 6 节 WU-0。本文记录「新写的 World vs 仓库已有实现」的取舍结论，
以及本轮验收场景的冻结定义。后续 WU 以此为准，不再重复论证。

核对基线：分支 `feature/headless-runtime`，HEAD `3ac11ba`。

---

## 1. 取舍结论

判据用 `docs/17 §3.2` 的三个问题：
① 换一个游戏仍有意义吗？② 关掉编辑器独立运行还需要吗？③ 换 CLI 执行规则应该相同吗？

### 1.1 实体状态表：废弃 `runtime/World`，改用 `CharacterTable`（`@aether/gameplay`）

| | 新写的 `runtime/World` | 已有的 `CharacterTable` |
|---|---|---|
| 身份 | 数组下标，无 generation | **generation 单调递增**，槽位复用后旧身份必然失效 |
| 分离 | O(n²) 全对全 | 供 `CrowdSolver` 用的 `SpatialHash` 邻域查询 |
| 破对称 | 无（正面僵持会锁死） | `dodgeBias` ±1，两只 NPC 总往同侧错身 |
| 目标/状态 | 无 | `targetEntity` / `behavior` / `alertLevel` / `speedScale` |
| 池化 | 无 | `CharacterPool` + freelist |

**决策：废弃自研 World。**

理由：
- `docs/17 §3.5` 明令「每类运行状态只能有一个权威 owner，禁止长期同时维护两张
  可独立修改的角色状态表」。当前正是两张（World + CharacterTable）。
- `docs/17 §5.1` 要求「引入槽位复用时必须防止旧身份命中新实体，可评估复用已有
  generation 机制」—— `CharacterTable` 已有现成 generation，自研版本要重造一遍。
- 自研 World 只活了一天，没有历史包袱，正是替换成本最低的时刻。
- `CharacterTable` 是纯 CPU、零 DOM/GPU 依赖，符合 headless 约束
  （`docs/17 §3.5`：headless 只要求与 DOM/GPU/真实时间解耦，**不要求**禁止复用 `@aether/*`）。

**适配点**：`CharacterTable` 用数字 `defId`，场景 `SpawnPoint.characterId` 是字符串
（`'E-01'`）。需要一条 `characterId → defId` 的持久化映射 —— 见 §2。

### 1.2 移动与避障：改用 `FlowField` + `CrowdSolver` + `SpatialHash`（`@aether/ai`）

`packages/ai/src/navigation.ts` 已完整实现：Dial 桶环 Dijkstra 流场积分（可跨帧恢复）、
chamfer 距离变换烘焙离墙间隙、贴墙推力、邻域分离、僵持检测。全是纯 CPU。

**决策：直接用。** 自研等于造第三个轮子，且 `docs/17 §8` 第 3 条明确要求
「本轮场景的障碍真实参与移动约束」—— 只有流场 + 代价场能满足，直线追击做不到。

障碍来源：场景里 `Collider` 且 `isTrigger === false` 的节点（floor-1 已有 6 个掩体）。
作用域：场景里唯一的 `NavZone`（floor-1 的 `nd_f1_nav`，66×16，cellSize 0.5）。

### 1.3 世界变换：改用 `SceneGraph.updateWorldTransforms()`（`@aether/scene`）

`sim-level.mjs` 里手写的 `worldPosition()` 只累加父节点 `position`，忽略旋转与缩放。
`SceneGraph` 已有正确实现（TRS 组合 + depth 升序传播），且已实现 ADR-014 的
`snapshot()` / `restore()` —— 正好是 WU-4「Stop 恢复作者状态」所需要的。

**决策：删掉手写版本，走 `SceneGraph.fromDocument()`。**

### 1.4 角色参数：新增 `assets/characters/stats.json` 作为真源

现状问题：`sim-level.mjs` 的 `statsOf()` 用 `parseFloat('1.4 m/s')` 从 roster 抠数字，
再用 `Boss ? 0.6 : 0.35` 硬编码半径。`docs/17 §5.3` 点名禁止：「不以 parseFloat 加默认
常数掩盖缺失配置」。

根因：roster.json 是**美术/设计资料库**（`height: "1.75 m"`、`speed: "1.4 m/s"`、
`attack.range: "扇形 90° / 2.2 m"`），承担不了 `CharacterDef` 需要的
胶囊半径 / 质量 / 转向速率 / 视野 / 听觉 / 攻击距离等运行时数值。

**决策：新增独立的角色参数真源，两份文件分工明确。**

| 文件 | 责任 | 消费方 |
|---|---|---|
| `assets/characters/roster.json` | 外观、叙事、威胁等级、AI 提示词（美术/设计） | 画布施工、资产生成 |
| `assets/characters/stats.json`（新） | 运行时物理与 AI 数值（程序） | `CharacterDef` 生成 |

**防漂移**：`content:check` 交叉校验 —— 解析 roster 的 `speed`/`height` 首个数值，
与 stats.json 比对，不一致报 error。两份真源不会静默各改各的。

### 1.5 唯一状态 owner 总表

| 状态 | 唯一 owner | 说明 |
|---|---|---|
| 作者场景数据 | `SceneDocument`（`.scene.json`） | 唯一持久化真源 |
| 运行时场景结构 | `SceneGraph` | 派生量（world/depth）不落盘 |
| 实体状态 | `CharacterTable` | 含 generation，唯一权威 |
| 角色定义 | `CharacterDef`（由 stats.json 生成） | 只读 |
| 导航/避障 | `FlowField` + `CrowdSolver` | 每会话一份，来自装载产物 |
| 会话推进与查询 | `RuntimeSession`（`packages/runtime`） | 固定步、输入、种子 |
| 快照场景 | 显式导出的 `.scene.json` | **派生产物**，不回写作者场景 |

## 2. 验收场景定义（从 floor-1 冻结）

`docs/17` WU-0 要求：一个可进入战斗房间、一个尚未进入的刷怪区域、一个障碍物、
明确玩家起点，实体规模 ≤ 24。

`assets/scenes/act1/floor-1.scene.json` **已经满足前三条**，只需补玩家起点：

| 需求 | 落点 | 现状 |
|---|---|---|
| 可进入战斗房间 | `nd_f1r0` 房间 1 · 战斗（20×16，中心 10,0） | ✅ 已有，含 3 个刷怪点 |
| 尚未进入的刷怪区域 | `nd_f1r2` 房间 3 · 战斗（20×16，中心 56,0） | ✅ 已有，含 3 个刷怪点 |
| 障碍物 | `nd_f1r0_cv0/cv1/cv2` 掩体 1–3 | ✅ 已有，均带 `Collider{isTrigger:false}` |
| 导航作用域 | `nd_f1_nav`（66×16，cellSize 0.5） | ✅ 已有 |
| **玩家起点** | — | ❌ **缺失，本轮补 schema 字段 `playerStart`** |

实体规模：房间 1 = 5+4+3 = 12 只（E-01×9、E-02×3）；
房间 3 = 4+4+4 = 12 只（E-01×8、E-02×4）。合计 24，符合上限。

**临时模拟假设（不是产品行为，不得当作冻结基准）：**

1. 玩家在切片阶段**不移动**（无输入驱动）。WU-2 起由输入序列驱动。
2. 「进入房间」判定用**矩形 bounds 包含**玩家中心点，不用 Collider 触发器事件。
   真触发器系统属 Phase 2。
3. 刷怪后敌人**不再消失**（无战斗、无死亡）。
4. `CharacterDef` 的 `skeleton` / `bodyParts` / `animSet` / `animGraph` 本轮**全填 0**
   （尚未接入渲染资产），`bodyParts` 为空数组。这是显式的能力缺口，不是完成项。
5. `hurtboxes` 本轮为空 —— 无战斗系统。

**已知的旧结果失效**：`assets/scenes/sim/floor1-t{0,1,3,5}.scene.json` 是「所有房间
立即全部刷怪」时期生成的静态快照。改成房间进入触发后，这些快照不再代表当前规则，
属过期派生产物，保留作历史对照但**不作为本轮验收基准**。

## 5. WU-3 落地记录（动态实例渲染）

### 5.1 关键约束（调研阶段确认）

动态实体**不能**进入静态 `SceneGraph` 与 `MAX_OBJECTS`（64）槽位 —— 24 只僵尸就占掉
三分之一，500 只根本不可能。`MAX_OBJECTS` 的根因是 `renderer-core.ts` 里
`transformBuf` 的 buffer 大小（64 × 256B）；shader 侧 `scene.wgsl` 的
`transform` 是**单个** uniform 不是数组。所以动态实例**不碰 transformBuf**，
另开 storage buffer 就绕开了。

调研同时确认：全仓 instancing **完全不存在**（8 处 `drawIndexed` 的 instanceCount 全是 1，
无 `drawIndexedIndirect`，VAT 只有枚举没有任何渲染器读它）。WU-3 是全仓第一条 instancing 路径。

### 5.2 实现落点

| 层 | 文件 | 内容 |
|---|---|---|
| 引擎 | `packages/render/src/shaders/dynamic.wgsl.ts` | 新 WGSL：`vs_main` / `vs_outline` / `fs_main` / `fs_outline`；实例走 `@binding(3) var<storage, read> inst: array<DInst>`，用 `@builtin(instance_index)` 取行 |
| 引擎 | `packages/render/src/renderer-core.ts` | `CoreDynamicBatch` + `DYNAMIC_INSTANCE_FLOATS=12`；`dynamicLayout` / `dynamicPipeline` / `dynamicOutlinePipeline`；`drawDynamicBatches()` 插在 pass 1 的 `pass.end()` **之前** |
| 编辑器 | `apps/editor/src/services/runtime-bridge.ts` | `RuntimeBridge`：`attach(session)` / `refresh()` / `batches()` / `select()` / `pickRay()`（**WU-4 之后不再持有运行状态机** —— 见 §6.1） |
| 编辑器 | `apps/editor/src/renderer.ts` | `setDynamicBatches()` 注入口 + `getDocument()` + 两个 debug 断言口 |
| 编辑器 | `apps/editor/src/main.ts` | 渲染循环把 Bridge 批次注入 `setDynamicBatches()`；HUD 运行时行；运行时实体优先拾取 |

> ⚠️ 上表第一、三行在 WU-4 之后曾一度失准（仍写着 `bridge.start(doc)` / `bridge.advance(dt)`，
> 以及运行时特有的 `screenRay()`）。WU-6 的独立评审把它作为「文档漂移」抓了出来并已订正：
> **状态机在 `PlaySession`，Bridge 只翻译；射线只有 `renderer.pointerRay()` 一份。**

### 5.3 三个设计决定

1. **复用 pass 1 的 MRT + depth，不另起 pass**。动态实体因此自动参与 toon 分阶、雾、
   inverted-hull 描边、bloom / tonemap / 半调等全部后处理，与静态关卡是同一束光。
2. **按体型分组成多个 batch**（`meshId = capsule:r0.340:h1.750`）。网格按 (radius, height)
   生成并缓存，改体型即换 key。代价是「体型种类数」个 draw call（≤9），远好于 500。
   `GraphicsBuffer` 缓存归 core（ADR-001），调用方每帧传全量也不会重复上传。
3. **不引入第二套高亮管线**：选中 = 实例色 ×1.9。淡而无害，且不会误伤静态关卡的
   选中/悬停两层描边。

### 5.4 踩坑：WGSL 编译错误只有实机能抓

第一版把 `toon` 的 bind group visibility 写成只给 `FRAGMENT`，而 `vs_outline` 要读
`toon.outline` 算描边宽度 → 运行时 `CreateRenderPipeline` 直接抛
`Entry point's stage (ShaderStage::Vertex) is not in the binding visibility`，
编辑器进 fatal 页。

**`tsc --noEmit` 全绿、`vite build` 全绿、500 条单元测试全绿** —— 一条都拦不住。
只有 headed Chrome + 真实 GPU 打开页面才暴露。修法：toon 的 visibility 改成
`VERTEX | FRAGMENT`。

→ 与记忆里「WebGPU 编码期陷阱」完全一致：**每次新增 pipeline，必须实机跑一次**。

## 6. WU-4 落地记录（Play / Pause / Step / Stop）

### 6.1 责任切分：状态机从 Bridge 里搬走

WU-3 的 `RuntimeBridge` 同时管了「渲染翻译」和「运行调度」两件事，违反
docs/18 §1.5「每类运行状态只能有一个权威 owner」。WU-4 把它拆开：

| 模块 | 归属 | 职责 |
|---|---|---|
| `packages/runtime/src/play-session.ts` | **runtime 包（纯 CPU 可测）** | 状态机 `stopped/playing/paused`、固定步累加器、启动失败清理、启停计数 |
| `apps/editor/src/services/runtime-bridge.ts` | 编辑器 | 只做「世界 → 批次」的翻译。`attach(session)` / `refresh()` / `batches()` |
| `apps/editor/src/services/play-controller.ts` | 编辑器 | 只做装配：快照/恢复作者态、推进后同步 Bridge、通知 UI |

放进 runtime 包的理由：状态机一旦散在 UI 代码里，就会出现「按钮显示暂停但循环
还在推进」这类**只有实机才复现**的鬼故事。纯 CPU + 确定性的东西就该放可测的地方。

### 6.2 相机：A 方案（不引入游戏相机）

WU-4 开工前跟用户确认过两个选项，按默认 A 落地：

- **A（已采用）**：不引入游戏相机，编辑相机在 Play 中照常自由移动。
- B：切到关卡的 `Camera` 组件（55° god view），Play 就是"真的在玩游戏"。

选 A 的理由：docs/17 的要求是「检查视角可以自由移动，不能反向改变玩家状态」——
编辑相机写的是 `camera` 对象，玩家位置在 RuntimeSession 的实体表里，两条路径本来就
互不干涉。加一个游戏相机反而让「改之前 / 改之后」没法同机位对比。
**B 留到 WU-2 后半（玩家能动）再补。**

### 6.3 作者状态的保存与恢复

- Play 前 `renderer.snapshotAuthorState()`：只存**可序列化的编辑态**（pos/rot/quat/
  scale/visible/removed/pickable/name/category/subMeshes.visible），**不存 GPU 资源**
  → Stop 时原地写回，零 GPU 重建。
- Stop 时 `restoreAuthorState()`：数量一致逐个恢复；不一致则按索引恢复能对应的，
  其余保留并 `console.warn`（宁可残留一个改动，也不要索引错位张冠李戴）。
- **不从磁盘重载** —— docs/17 WU-4 明确禁止，作者可能刚拖完掩体还没保存。
- Play 中禁掉增删（Delete 键 + 层级面板删除都拦），因为快照按索引恢复、数量必须一致。
  变换 / 材质 / 参数照常允许改。

### 6.4 UI 与快捷键

工具栏（`#gizmo-bar` 最前面新增一组）：`▶ Play` / `⏸ 暂停` / `⏭ 单步` / `↻ 重跑` /
`■ 停止`。按钮的文案与启用状态**全部由 `PlayController.state` 推导**，不存第二份状态。

## 7. WU-5 落地记录（一个可保存的局部修改闭环）

### 7.1 责任切分：作者文档归 store，编辑器只做 IO 与控件

| 模块 | 归属 | 职责 |
|---|---|---|
| `packages/runtime/src/spawn-edit.ts` | **runtime 包** | `SpawnEdit` 领域命令（field + nodeId + from/to）、校验、`SpawnEditStore`（工作副本 + 撤销栈 + dirty） |
| `packages/runtime/src/spawn-ab.ts` | **runtime 包** | `captureInitialScatter()` 同种子初始散布指纹、`compareScatter()` 逐刷怪点做差、`describeDelta()` |
| `packages/runtime/src/doc-diff.ts` | **runtime 包** | `changedJsonPaths()` 逐路径比对纯数据 |
| `apps/editor/src/services/spawn-panel.ts` | 编辑器 | 把 vm 画成 DOM，把动作转成回调。**不持有状态、不校验、不碰文档** |
| `apps/editor/src/main.ts` | 编辑器 | 三件事：画控件、写文件（`writeProjectFile`）、把改动送进 Play |

`SpawnEditStore` 构造时把文档拷成两份：`committed`（磁盘版）与 `document`（工作副本）。
**工作副本是唯一真源** —— `renderer.setDocument()` 之后渲染器与 `PlayController` 都读它，
「编辑后要不要同步给谁」这个问题就不存在了。

### 7.2 为什么是「领域命令」而不是通用 setPath

命令知道自己改的是 `SpawnPoint.radius`（**生成散布半径，米**）而不是碰撞半径，于是能：

1. 给出有语义的校验（负数 / 非整数 count / 50 米以上都是作者笔误）；
2. 自己算出 `from` → `to`，**撤销不需要存文档快照**（栈里每条只有几十字节）；
3. 让「这次到底动了几个字段」变成一个可断言的集合 —— 通用 setPath 做不到第三条。

本轮只开 `radius` / `count` 两个字段（docs/17 WU-5 的原话）。
`wave / trigger / delaySec / prefab` 各自牵扯运行语义，加进来等于把 WU-5 变成半个 Inspector。

### 7.3 保存前的自检：改动集合必须恰好等于预期

`changedJsonPaths(committed, working)` 逐路径比对。一次 radius 编辑的期望结果是
**恰好一条** `nodes[7].components[0].radius`。

这是「保存保留未消费组件和无关字段」唯一的可靠断言方式：声称"没动别的"没有意义，
得让差异集合精确等于预期那一条。多一条 = 顺手动了别的东西；少一条 = 编辑没生效。
`saveSpawnEdits()` 在写盘**之前**再跑一次同样的自检，非刷怪点字段的改动一律拒绝保存
（将来有人加新命令也不会悄悄破坏这个性质）。

保存内容补了行尾换行 —— 否则每次保存都会多出一条
`\ No newline at end of file` 的噪声 diff。

### 7.4 A/B：同种子重跑，比的是初始散布

`captureInitialScatter()` 用**同种子重新装载**抓指纹，不碰正在播放的会话。
比的是 tick 0 的散布，而不是"跑 N 帧之后"：跑起来之后的位置由寻路/分离/障碍共同决定，
是**下游噪声**，不是这次编辑的直接结果。tick 0 的散布才是 radius 这一个变量的干净函数
（`r = sqrt(u) * radius`，mean 与 max 都随 radius 单调）。

每次编辑自动抓 A（编辑前）与 B（编辑后），面板显示 `before → after` 而不是只显示改后 ——
只展示"改完之后"，作者判断不出改动是真生效了，还是被触发条件吞了（房间还没进 → 一个都没刷）。

### 7.5 🔴 顺带修掉一个会让本轮验收立不住的运行时缺陷

原先所有刷怪点**共用一条 RNG 流**（`this.rng()` 顺序消耗）。于是改 A 的 `count`
会多消耗几个随机数，把 B、C 的取点**整体平移** —— 作者以为在做局部编辑，实际整关重排一遍。

这个缺陷在 WU-5 之前不可见：没有任何用例比较"两个 count 不同的场景的同一刷怪点"。
是 A/B 测试断言 `changedNodeIds == [target]` 在改 count 时挂掉才暴露的
（改 radius 不挂，因为它不改变取数个数）。

修法：每个刷怪点用 `mixSeed(会话种子, nodeId)`（FNV-1a）派生自己的流。
混入会话种子而不是只用字符串哈希，是为了让"换种子重跑"仍然整体改变散布。
`reset()` 不再需要"重新播种一条共享流" —— 派生流天然回到初始态。

性质由 `session.test.ts` 三条新断言锁死：改 `nd_f1r0_sp0` 的 count，
`nd_f1r0_sp1` 的初始位置逐位不变；总数变化正确；换会话种子仍然整体变散布。

探针会真的写一次场景文件（「保存」是 WU-5 的核心要求，不落盘验证不到）。
第一版拿 `renderer.getSceneSource().url` 直接拼 `/__fs/file?path=`，而那个 url 带

1. `/__fs/file` 与 `/__fs/write` 的路径都要先 `replace(/^\/+/, '')`

2. **写用户资产的验证脚本，还原必须放在 `finally` 里**，且校验失败也要还原。

### 8.1 §8-1 同源同输入一致性：先证明"输入相同"，再谈"输出相同"

**这一条最容易做成假的。** 只要两侧各自"从磁盘读了一遍"，就默认输入相同 —— 但编辑器
手上的那份文档可能已经被未保存编辑改过、被迁移链补过字段、被归一化过顺序。任一条成立，
实体位置就会分岔，而分岔的样子跟"一致性坏了"**一模一样**，排查会直接走错方向。

所以先加了输入指纹：`sceneFingerprint(doc)` = 对 `stableJson(doc)`（键按字典序）做
FNV-1a 32 位。两侧各自对自己**实际喂进 runtime 的那份文档**取指纹，相等才继续比对实体。

| 项 | 实测 |
|---|---|
| 入口（两侧同一个） | `PlaySession.play(doc)` + `RuntimeSession.step()` |
| Node 侧 | `tools/verify/runtime-parity.mjs`（esbuild 打包产物，**只读**：不写场景、不改 project.json） |
| 浏览器侧 | `window.__editor.runtime.runTo(seed, ticks)`（自建自停，不碰用户正在播放的会话） |
| 输入指纹 | `web=7adf8152 node=7adf8152`（相等） |

| 到达 tick | 60 = 60 |
| **逐实体身份 / 位置 / 目标 / 状态** | 13 个实体，`maxΔ = 0.00e+0`（容差 1e-9，身份按 `id:generation` 配对） |
| 换种子（7 → 48）仍一致 | `maxΔ = 0.00e+0` |
| 不同种子确实产生不同结果 | ✅（证明"一致"不是恒等） |

逐字段全等，`x` / `z` / `yaw` 逐位相等。**这才是"同一个世界"，而不是"一边也刷了 13 只"。**

### 8.2 §8-5 画面对应：点在它身上，选中的就是它

做法上踩过一次坑：一开始试图"把相机对准它再投影"，结果投影出 `x=12683`（近平面爆掉的特征）。

把它的像素坐标交给**真实点击入口**（`pickAtClient`，即 mousedown 走的那条路），

### 8.5 踩坑：固定调试端口会接管上一轮残留 Chrome 的旧页面

**症状**：同一份探针，跑一次全绿、再跑一次 §8-1 报"输入指纹不等"（`web=7f7f2600 node=7adf8152`，
差异恰好一处 `nodes[7].components.0.radius: 4.75 vs 1.5`），§8-5 报"画面里没有可见实体"，
`eye=[0,0,0]`、所有实体投影 y 恒为 77.9（退化矩阵）。

**排查**：磁盘干净（`git status` 无改动、Node 读到的就是 1.5）、dev server 用原生 `https.get`
取到 1.5、`/__fs/file` 也确实发了 `Cache-Control: no-cache`。所有**服务端**证据都说 1.5，
唯独"页面启动时"看到 4.75 —— 那就只剩"这个页面不是本轮新开的"。

**根因**：探针用**固定**调试端口 9336，且结束时不等 Chrome 真正退出。上一轮的 Chrome 还没退干净时，
本轮的 `httpJson(9336)` 连上的是**上一轮的实例**，`json/list` 里那个旧页面被当成本轮页面接管；
旧页面带着上一轮"保存后"的内存文档（radius 4.75），于是输入指纹不等、相机取证全零。

**修法（三条一起，缺一条都还会复现）**：

1. 调试端口每轮唯一（`9300 + pid % 600`）；
2. 接管前验明正身：`performance.now()` 超过 30s 就判定陈旧，改用 `Target.createTarget` 新开 tab；
3. 结束时 `await` 进程真的 `exit` 再返回；顺带 `Network.setCacheDisabled` 关掉 HTTP 缓存
   （`/__fs/file` 只发 `no-cache`、无 `ETag`，没必要让陈旧响应混进结论）。

**教训**：验证脚本的"被测对象身份"本身就是一条隐含断言。端口固定 + 不复验页面年龄 =
把上一轮的幽灵当成本轮的结果，而且症状跟真实缺陷无法区分。**这条比任何一条业务断言都更值钱**，
因为它会让全部断言一起说谎。

### 方法论（复审点名，值得留下）

- **校验与写入必须在同一个受控操作里** —— 一切「先查后写」的客户端两步协议都有

| P1 | **直接写文件不受队列保护**：`rename` 前仍有窗口，且进程内队列约束不了别的程序 | 在 devfs 文件头写死**写入协议**：`/__fs/write` 是唯一受协调写路径；409 的保护范围 = **经过 API 的写者**；直接 `fsp.writeFile` 不受保护；rename 前窗口不可在本机无锁文件系统上彻底消除 —— **不宣称完整保护** |

实测：`verify:fs` 24 条全过（含新增并发与失败恢复）；`npm test` 597 条 / 33 文件；
`typecheck` / `editor:build` exit 0。

### 教训（值得留下）

1. **Promise 队列里，存的、等的、清的必须是同一个对象。** 存派生 Promise、等原始
   Promise，等于把错误处理挂在一个没人等的对象上 —— 这在 Node 里不是静默，是**进程级崩溃**。
2. **跨执行环境的 import 约定要按最严的那个写。** vite/esbuild 宽容无扩展名，
   Node ESM / strip-types 不宽容 —— 给会被多环境加载的文件写 import 时，一律带显式扩展名。
3. **保护边界要说清楚，而不是说满。** 队列保证的是"经过 API 的写者互不可覆盖"；
   直接写文件不在内。把 ④ 写进协议头部，比事后被审计戳穿便宜得多。
