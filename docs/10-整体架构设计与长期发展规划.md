## 2. 架构决策（有主见，可反驳）

### 决策 D1 — 确立单一引擎基座，编辑器下沉为"消费者"
**不要**再往 `apps/lab` 里堆渲染逻辑；**也不要**另起炉灶重写引擎。
- 把 `apps/lab/shader-lab` 里已验证的 `renderer / gltf / materials / geometry / math` **上提（upstream）为 `packages/render`、`packages/gfx`、`packages/scene` 的首个真实实现**。
- 编辑器重构为 `apps/editor`，从 packages 导入，而非自带渲染器。
- 代价是一次性的重构，收益是：编辑器从"原型"变成"引擎的参考实现 + 验收场"，所有规划里程碑都有可运行载体。

### 决策 D2 — 依赖脊线，不为空包建目录
只建有真实代码的包，沿依赖方向生长：
`core → gfx → framegraph → render → scene`，横向 `ai / gameplay`（已存在）挂在 `scene` 之上。
规划里的 `platform/physics/vfx/ui/audio/input/script/net` **按里程碑按需创建**，不要在 M0 阶段预建空壳。

### 决策 D3 — 内容上提为 typed binding 层（"资料库即代码"）
`roster.json` / `tokens.json` 是优秀真源，但引擎目前消费的是 `packages/gameplay` 里的 `CharacterDef` 手工接口，二者没有桥。
- 增加 `content/` 包：`roster.json` + `tokens.json` 经脚本生成 `roster.generated.ts`（强类型 Table 初始化数据），引擎只认生成物。
- 这样"改 roster.json → 重跑生成 → 类型检查卡住非法字段"形成闭环，资料库与运行时强一致。

### 决策 D4 — 验证体系标准化并纳入 CI
docs/09 的三层验证（Node 直测数学 / headless WebGPU / CDP 视觉像素判定）是全项目最值钱的方法论，**提升到引擎级标准**：
- `vitest` 覆盖 math/gltf/geometry/materials（已有 55 例，扩到全引擎）。
- headless WebGPU（Chrome 152 + `--enable-unsafe-swiftshader`）做渲染冒烟。
- CI 跑这两层；CDP 视觉判定作为可选门禁。
- 解决"本环境 headless 跑不了 WebGPU"的假阴性（已证伪，见 docs/09 §7）。

### 决策 D5 — 3D 资产生成管线工具化
混元 3D → `decimate_cluster` → `bake_lowpoly(xatlas)` → `export_labmesh --ao-bake --up-flip` → 导入，已对 E-04 跑通。把它固化成 `tools/asset-pipeline`，8 角色 + 环境道具统一复用，**减面质检以"表面积保持率 >80%"为硬判据**（docs/08 结论）。

## 3. 目标架构

```
┌──────────────────────────────────────────────────────────────────────┐
│ L6  Tooling & Editor                                                  │
│   apps/editor (由 apps/lab 重构而来) ── 消费下方所有包，自身不含渲染器    │
│   tools/asset-pipeline (3D 资产生成) · tools/baker · tools/shaderlab    │
├──────────────────────────────────────────────────────────────────────┤
│ L5  Gameplay & Subsystems                                             │
│   packages/ai (流场寻路/战斗/行为 ✓) · packages/gameplay (SoA 角色 ✓)    │
│   + 后续: physics / vfx / ui / audio / input (按需建)                   │
├──────────────────────────────────────────────────────────────────────┤
│ L4  Scene & Asset                                                     │
│   packages/scene (World/Transform/Camera/LOD)                         │
│   packages/assets (glTF 导入 ← 来自 apps/lab/gltf.ts 上提)              │
│   content/ (roster.generated.ts ← roster.json/tokens.json)             │
├──────────────────────────────────────────────────────────────────────┤
│ L3  Renderer                                                          │
│   packages/render ← apps/lab/renderer.ts + shaders 上提               │
│   (toon + inverted-hull 描边 + 材质三层 + 逐子网格，先单对象，再长 Clustered)│
├──────────────────────────────────────────────────────────────────────┤
│ L2  FrameGraph      packages/framegraph (Pass DAG ✓ 雏形)              │
├──────────────────────────────────────────────────────────────────────┤
│ L1  GPU Abstraction  packages/gfx (device/分配器 ✓ · handle ✓)         │
├──────────────────────────────────────────────────────────────────────┤
│ L0  Platform        packages/core (app/ecs/math ✓ 雏形)               │
└──────────────────────────────────────────────────────────────────────┘

依赖规则（强制）：只允许向下依赖。Editor 依赖全部，没有任何包依赖 Editor。
content/ 只被 scene/gameplay 读取，反向零依赖。
```

**关键变化**：`apps/lab/shader-lab` 不再是一个"带渲染器的独立 app"，而是 `packages/render` 的**第一个调用方与验收场**。渲染逻辑只存在于 packages 一处。

## 4. 长期发展规划（引擎 × 游戏 双轨）

规划里的 M0–M8 是纯引擎视角，缺了"末日尸潮"游戏本身的里程碑。下面把它补齐成**双轨**，并让编辑器在每一阶段都充当集成与验收点。

| 阶段 | 时长(估) | 引擎交付 | 游戏交付（末日尸潮） | 验收（来自既有真源） |
|---|---|---|---|---|
| **Phase 0 · 并轨与基座** | 1–2 月 | D1–D5 落地：renderer/gltf/materials 上提；content/ 生成层；CI 三层验证 | 资料库→运行时打通（roster.generated.ts 驱动角色表） | 编辑器仍能渲染 E-04，且渲染代码已不在 app 内 |
| **Phase 1 · 垂直切片：一只僵尸** | 1–2 月 | M1 ECS+Transform+Camera+FrameGraph+glTF；M2 PBR 直接光+CSM+IBL+TAA | Act1 城郊公路：E-01/E-02 从 roster 渲染进基础场景 | 单角色 toon+描边+阴影对标规划 M2 |
| **Phase 2 · 尸潮模拟** | 2–3 月 | M3 GPU 剔除+Clustered Forward+（千光源）；M4 compute skinning+动画图；M5 物理+角色控制器 | Act2–3：500 僵尸流场寻路+群体避让+战斗+包围圈配额（**packages/ai 直接复用**） | 500 僵尸 60fps；AI 包已就绪，接 scene 即可 |
| **Phase 3 · 完整游戏系统** | 2–3 月 | M6 VFX/粒子/UI/音频/输入映射 | Act4 生化医院 + 肉鸽元系统（3 选 1 强化/补给站/战利品卡，对应美术批次 P2/P3） | 4 幕可玩通关；横屏 HUD（ardot 9 屏）接入 |
| **Phase 4 · 工具与规模** | 2–3 月 | M7 资产烘焙+.pak 流式+地形 LOD；M8 编辑器成熟（Inspector/Gizmo 已证明/Play-in-Editor/热重载） | 全 8 角色 3D 化完成（tools/asset-pipeline 批量）；大世界关卡 | 无缝大场景；编辑器生产可用 |

> 总周期估算 **9–13 个月**（单人/小团队，按当前产能）。Phase 0 的并轨是杠杆点——不做它，后续每个里程碑都要在"两套代码"间反复横跳。

## 9. 库采纳清单（自实 vs 用库）

> **用户决策（2026-09-02）**：按原始文档 `docs/01-09` **全量自实渲染管线**（Clustered Forward+ / GPU-driven 剔除 / FrameGraph / toon+描边），**不降格砍功能**；管线**底下**的标准件复用成熟库。
> 这并非"降格"——自实管线与复用底层库**并存**，正是 `docs/01` 技术选型表的精神（物理用 Rapier、解码走 WASM）。

| 层 | 决策 | 选型 |
|---|---|---|
| 渲染管线架构 | **自实**（plan 核心，无库可替） | Clustered Forward+ / GPU 剔除 / FrameGraph / toon+描边 |
| ECS / SoA | **自实**（引擎灵魂） | 沿用 `packages/core` + `packages/gameplay` 手写 SoA |
| 热路径数学 | **自实** | 每帧 `Float32Array` 承载（plan 已定） |
| 物理 | **用库** | `Rapier (WASM)`（plan 已定） |
| 纹理/网格编解码 | **用库** | `KTX2/basis_universal (WASM)`、`meshopt (WASM)` —— 绝不手搓 |
| glTF 处理 | **用库**（周边） | `@gltf-transform/core` 做处理/优化/减面衔接；自有 `apps/lab/gltf.ts` 导入器保留 |
| WGSL 工具链 | **用库** | `naga`(Rust/WASM) / `tint`(C++) 供 `tools/shaderlab` 变体展开+校验，不自写 parser |
| 数学（非热路径） | **用库** | `gl-matrix` / `wgpu-matrix` |
| Worker RPC | **用库** | `comlink` |

## 10. 决策记录（ADR 索引，续）

- **ADR-004**：渲染管线按原始文档全量自实，底层标准件复用库（物理 Rapier / 编解码 KTX2+meshopt / glTF gltf-transform / WGSL naga+tint / 数学 gl-matrix / Worker comlink）。明确**不降格砍功能**，且"自实管线 ≠ 自搓所有底层"。参考实现见 §8，库清单见 §9。
