# 23 · 战斗层设计（ADR-019）

> **Status**：Proposed
> **一句话**：给 runtime 补上「能打死、会被打死、有波次推进、有胜负」的最小完整
> 战斗内核 —— 让 floor-1/2/3 从「AI 演示场」变成「可玩关卡」。
> 这是 ADR-018（docs/22）WU 队列中 P5 的设计前置。

## 2. Decision

### 2.0 分层：战斗内核 vs 行为脚本 vs Build

```
Build 系统（天赋/武器特性）      —— 不在本期（挂载点预留）
        ↓ 消费
战斗内核（runtime 内建，本设计） —— 血量/伤害/波次/死亡/胜负
        ↓ 触发
行为脚本（assets/behaviors）     —— 战斗事件驱动的自定义反应（ADR-017 已落地）
```

**为什么战斗内核不做成行为脚本**：血量/波次是**所有实体共有的结构语义**，
做成逐节点脚本等于把系统逻辑散进内容层 —— 违反 docs/17 §3.1（当前游戏规则层
的 owner 是 runtime）。行为脚本留给「这一层的这个房间要放毒气」这类**定制**。

### 2.1 血量与伤害（CombatState，SoA）

**既有列的处置（必须先裁决，否则出现两列血量 = 双 owner，违反 docs/17 §3.5）**：

`CharacterTable` 已有 `health / poise / cooldownUntil`（character.ts:117-119），
alloc 写死 1、全仓零消费 —— 是**占位列**。裁决：

| 既有列 | 处置 | 理由 |
|---|---|---|
| `health` | **复用并重定义**为本设计的 hp（真实血量，来自 stats 真源） | 名字语义就是血量；另起 `hp` 列 = 同表两列血量，审计灾难 |
| `poise` | **保留闲置**（霸体，GDD 硬核项②的挂载点，本期不用不删） | 删了将来还得加回来 |
| `cooldownUntil` | **复用为攻击 CD**（语义一致：到点才能再动） | 同 health 逻辑 |

新增列（既有表无对应语义）：

| 列 | 类型 | 说明 |
|---|---|---|
| `maxHp` | Float32Array | 上限（来自 stats 真源）；health 复用后配套 |
| `hitFlash` | Float32Array | 受击高亮剩余秒（渲染层消费，`[PLACEHOLDER 0.15]`） |
| `windup` | Float32Array | 前摇剩余秒（>0 = 正在蓄力，roster 的 telegraph 语义；cooldownUntil 语义改为"CD 到点时刻"配 tick 用） |

### 2.1a 与 packages/ai/src/combat.ts 的关系（裁决）

`combat.ts` 是一套**更完整的战斗框架**（动画时间轴命中窗口 / 扫掠 / DamagePipeline /
AttackTokenPool），从 ai 包公开导出但零外部消费。本设计的四态机与它**不是替代，
是先行简化 + 后续吸收**：

| combat.ts 组件 | 本期处置 | 对齐路径 |
|---|---|---|
| Montage/AnimNotify | **不用**（P4 动画未落地，无时间轴可挂） | 🔴 `windup` 计时列是 Montage 路线的**临时实现**——combat.ts 文件头硬规则「命中窗口由动画时间轴定义，不用代码计时器」在 P4 接线时生效，届时 windup 列退役为 Montage 采样源 |
| 扫掠命中（HitDedupeBuffer） | C3 玩家射线**先用单帧**（手枪瞬时弹道无扫掠需求） | 近战敌人接入时（C3 后）换 combat.ts 的扫掠 + 去重 |
| DamagePipeline（modifier 链） | **不引入** —— 与 applyDamage 单入口互斥 | Build 系统落地时，applyDamage 内部调 DamagePipeline 做修饰（单入口不变，管线成内核实现细节） |
| AttackTokenPool（群战名额） | **不引入**（CrowdSolver 已防挤爆） | 群战围殴调优时（P11 前）评估接入 |
| `AttackDef.poise` 语义 | poise 列**保留**正是它的挂载点（伤害附带削韧，GDD 硬核项②） | 硬直打断实现时消费 |

**一句话**：本期四态机 = combat.ts 的「无动画版先行切片」；两者共存期间以
applyDamage 为唯一伤害事实出口，combat.ts 的组件按上表节奏逐个接线。

伤害入口只有一个：

```ts
applyDamage(targetSlot, amount, source): DamageResult
```

- 减 health → ≤0 时 `kill(slot)`；**不直接 destroy**（死亡有视觉期，见 §2.3）
- 返回 `{ died, hpAfter }` —— HUD/音效/行为脚本都消费这个结果
- 🔴 伤害永远走 `applyDamage`，禁止任何路径直接写 `health` 列（否则"受伤高亮/
  击杀统计/经济掉落"这些派生反应全部漏掉，且无法审计）

### 2.2 NPC 攻击（近战挥抓，内建两态扩展为四态）

现有 `behavior: 0=idle / 1=chase` 扩展：

| 码 | 态 | 转移条件 |
|---|---|---|
| 0 | idle | 无目标 |
| 1 | chase | 追击中；**距离 > attackRange** 时移动 |
| 2 | **windup** | 距离 ≤ range → 前摇 `windup` 秒（roster 值），可被打断 `[PLACEHOLDER：仅硬直打断]` |
| 3 | **strike** | 前摇结束 → 对扇形内玩家 `applyDamage(attack.damage)` → 进 CD |

数值全部读 stats/roster 真源（如 E-01：挥抓 8 伤 / 1.6s CD / 2.2m 扇形 90° /
0.8s 前摇）—— **不在代码里出现任何魔法数字**。

### 2.3 玩家攻击与死亡回收

**玩家攻击（最小闭环）**：方向键已有；补一个动作键（P7 的虚拟按键先行接入
编辑器侧 `setFire(down: boolean)`）。射击 = 固定步内射线/扇形检测：

```
玩家朝向 yaw、射程 weapon.range、伤害 weapon.damage
命中 = 最近的首个 NPC（胶囊求交，runtime-bridge 已有 rayCapsuleY 可上提复用）
```

武器表第一期只有 1 把（手枪 `[PLACEHOLDER: dmg 12 / cd 0.35s / range 18m]`，
rationale：E-01 hp60 → 5 枪一只，验证 TTK 手感基线）。

**死亡回收**：`kill(slot)` → `hp=0`、`alive=false`、槽位推回 freelist（复用
CharacterTable 既有 generation 机制，防旧引用冒名）+ 触发 `onKill` 事件
（经济掉落/击杀数的挂载点）。**视觉尸体不在本期**（死了即消失，标注为已知简化，
不假装做了尸体动画）。

### 2.4 波次推进（WaveScheduler，runtime 内建）

把 `loader.ts` 的 `wave` 字段从「未实现警告」变为真实语义：

```
房间触发(room-enter) → 该房所有刷怪点按 wave 分组 → wave 1 立即投放
wave N 清空（房内 alive 敌数 = 0 且无待投放）→ 间隔 interWaveSec
→ wave N+1 投放 …… 直到最后一波 → 房间标记 cleared
```

- 每波的组成 = 刷怪点自带（`count` 是**总数**，按 wave 数均分 `[PLACEHOLDER:
  均分策略，playtest 后改加权曲线]`）
- **房间 cleared 事件**是经济/通关的挂载点（GDD §6 的层末结算锚这里）
- 同种子重跑必须产出相同波次时序（确定性，沿用既有 RNG 派生纪律：
  每个 (房间, wave) 用 `mixSeed(seed, roomId, wave)` 独立流）

### 2.5 胜负条件（最小集）

| 条件 | 判定 | 结果 |
|---|---|---|
| **本层通关** | 全部房间 cleared 且玩家存活 | 触发 `onFloorClear`（P10 关卡流程的挂载点：加载下一层场景） |
| **本局失败** | 玩家 hp ≤ 0 | 进入失败态：世界冻结（不再 step）+ `onGameOver` 事件；**不自动 Stop**（让玩家看清死状，UI 决定何时退） |

胜负是**事件不是轮询**：`applyDamage` 内判定并触发，宿主订阅。

### 2.6 数据契约（schema 扩展，走 ADR-013 迁移链）

场景侧新增（`SCHEMA_VERSION` 3 → 4，必须带迁移 + 测试）：

| 位置 | 字段 | 说明 |
|---|---|---|
| `SceneDocument` | `loseCondition: 'player-death'` | 胜负规则第一步只硬编码这一种；留扩展位 |
| `SpawnPointComponent` | `wave`（已有，激活语义） | 不改结构，只改 loader 消费 |
| 武器 | stats.json `player.weapon`（**数值进真源链**）；content 包 `weapons.ts` 只放类型 | 场景不存（内建）；数值不绕过 content:check |

**stats.json 扩展**（真源追加，content:gen 同步）—— ⚠️ 这是**结构改造不是搬数**：
- 现状：stats.json 是**纯扁平数值表**（gen-stats.mjs 的 NUMERIC_FIELDS），
  **没有任何 hp 字段、没有 attack 子结构**（8 条目全查）
- C1 实际工作：`renderEntry`/`NUMERIC_FIELDS`/交叉校验从扁平 → 嵌套结构改造；
  roster 的 attack 是嵌套对象（windup "0.8 s" 等字符串），要做**单位解析**，
  且 E-03 damage 是 `"6 DPS"`、E-04 是 `"12 + 击退 + 眩晕 0.6 s"` **复合串** ——
  逐条定解析规则，不是机械取首个数字（E-03 的 DPS 与单击伤害语义不同，
  E-04 的击退/眩晕进 `attack.extras` 留待 C3 后消费）
- player 与 npc 的 attack 结构不同（weapon vs 近战），交叉校验规则分叉设计

**武器数值的真源裁决**：手枪 `[PLACEHOLDER: dmg 12 / cd 0.35s / range 18m]`
落 **stats.json 的 `player.weapon`**（进 content:check 防漂移体系），
`weapons.ts` 只做类型定义不存数值 —— 不为武器开"TS 代码绕过真源链"的先例。

### 2.7 与行为脚本的桥（已有架构件直接用）

战斗事件可供 `assets/behaviors` 消费（ADR-017 执行器已在）。
**本期连 BehaviorContext 的接口都不改**（现状 `tick/runId/log` 三字段，
session.ts:426-439）——「留挂载点」指 C5 时在 runtime 侧发事件到
`session.behaviorEvents` 缓冲区，行为侧订阅 API 是后续 WU（接口改动需另立 ADR）。
示例行为仍是 debug-log。

**rayCapsuleY 归属**：从 `apps/editor/src/services/runtime-bridge.ts:47` 上提到
**packages/gameplay**（射线×胶囊是玩法域通用几何，不是编辑器专属）；
runtime-bridge 的 pickRay 同步改引，上提本身不改行为（纯搬家 + 引用替换）。

**C2 是地基**（所有后续都压在 applyDamage 单入口上）。

## 4. 验收定义（必须可复跑）

1. vitest：同种子下「玩家射击序列 → NPC 血量/死亡时序」逐位一致
2. vitest：wave 时序确定（wave2 投放的 tick 与组成可断言）
3. 浏览器：floor-1 第一间房（3 刷怪点混合编队 E-01×5 + E-01×4 + E-02×3，
   C4 重制后按 wave 分组），玩家用手枪清空 wave1 → wave2 出现
4. 浏览器：玩家被围殴致死 → 世界冻结 + 失败提示，Stop 仍能干净恢复
5. `aliveCount` 长时间跑**有减有增**，不再单调撞 512

## 5. Consequences

### 变得更容易
- 「打不死」这一 Play mode 最大硬伤拔除；HUD（P8）/经济/关卡流程（P10）有了事件锚
- 全部数值走真源链（roster→stats→runtime），playtest 调参改 JSON 不改代码

### 代价 / 明确不做（本期）
- **Build 系统**（天赋/多武器）：挂载点留好，实现等战斗内核验证手感后
- **尸体视觉/死亡动画**：死了即消失（记为已知简化）
- **远程敌人/Boss 机制**（B-01 的钩子等）：四态机先只做近战，Boss 用同机制超参
- **受击硬直打断**（GDD 硬核项②）：`[PLACEHOLDER：第一期不实现打断]`
- P4 未完成前，被打/打人的仍是胶囊 —— 战斗逻辑先行，视觉随后

### 风险
- SoA 战斗列加入后 CharacterTable 变宽，500 实体下每步全列扫描的成本要在
  C3 后量一次（P11 性能验收的前哨）
