# Agent 优先 Game Editor：架构与下一阶段开发指导

本文供后续开发 Agent 直接执行。目标是保留现有 headless 成果，建立可观察、可控制、可局部修改的游戏开发闭环。

## 1. 决策与范围

采用“可独立运行的玩法内核 + 共享编辑能力 + 人的可视化 Bridge”路线。GUI 和 Agent 是能力的使用者，业务规则不能依赖某一种操作入口。

下一阶段目标：同一份场景和输入，在 Node 与浏览器中驱动同一个 runtime；人在编辑器中可运行、暂停、单步、检查实体，并修改一个可持久化参数后重新比较结果。

本阶段不开发 MCP、Codex Plugin、内嵌 Agent 聊天框，不复制完整 Unity Editor，不建设完整通用行为图、完整 Prefab 工作流或 500 个带骨骼角色的渲染系统。通用地形、光照、材质、动画模块遵循本文架构原则，但不因此在本轮同时开发。

推进顺序：确认责任归属 → 共享装载与运行契约 → 实时 Bridge 和最小动态批处理 → 一个局部修改闭环 → 按真实需求扩展行为与规模。

## 3. 高层架构原则

### 3.1 横向按领域，纵向按职责

地形、光照、材质、动画、导航等是领域划分。每个领域根据实际需要分出以下职责，不要求机械地把每一格拆成一个包。

| 层次 | 唯一责任 | 例子 |
|---|---|---|
| 数据契约 | 可持久化的结构、引用、校验、迁移 | SceneDocument、灯光组件、材质引用 |
| 通用运行能力 | 独立游戏仍需要的计算与运行状态 | 动画采样、光照渲染、碰撞查询 |
| 通用编辑能力 | 创建、修改、诊断、撤销和保存内容 | 材质覆盖、地形编辑、动画预览 |
| 当前游戏规则 | 这个游戏如何使用通用能力 | 房间触发、僵尸追击、波次流程 |
| 宿主与入口 | 环境接入、请求映射和结果展示 | CLI、浏览器输入、Inspector、未来 MCP |

动画模块不决定僵尸什么时候攻击；僵尸逻辑不实现骨骼采样。光照模块不硬编码火场房间的灯光值；场景数据提供配置。编辑器模块不拥有另一套游戏规则。

### 3.2 判定归属的三个问题

1. 换一个游戏仍有意义吗？若有，优先归通用领域能力；否则归当前游戏规则或内容。
2. 关闭编辑器，独立运行游戏还需要吗？若需要，归运行能力；否则可能归编辑能力。
3. 换成 CLI 执行，规则应该相同吗？若应该，就不能只实现在 CLI 或 GUI 入口里。

### 3.3 数据、代码和派生结果

- 代码实现算法与行为；具体游戏内容、节点、参数及引用遵循项目场景/资产契约落盘。
- 场景是游戏内容载体；资产通用数据放 sidecar；项目级配置使用已有项目容器指针。不要在 CLI 常数、UI 内存、userData 中新增正式玩法真源。
- 作者数据、运行状态、渲染表示是三种不同责任。运行副本和 GPU 表示可以存在，但要明确来源与同步方向。
- NodeId 标识作者节点；运行实体使用独立身份，并能追溯来源节点。一处刷怪点可以生成多个实体，不能把两种身份混成同一个 ID。
- 调试快照属于派生产物。允许显式保存为评审材料，但不能让运行实体自动成为作者场景的一部分。

### 3.4 Agent 优先的具体含义

能力必须可被程序调用，输入输出应明确，能定位对象、读取状态、限定修改、复现结果。它不等于零 UI，也不等于直接修改内部数组。

人通过 GUI、Agent 将来通过工具调用同一套领域操作。GUI 不额外实现规则，Agent 不绕过校验、撤销和保存语义。领域 API 现在即可建立，不以 MCP 为前提。

### 3.5 依赖和文件纪律

- Headless 要求与 DOM、GPU、真实时间采样解耦，不要求禁止复用所有 `@aether/*` 包。
- 先评估已有 CharacterTable、SpatialHash、CrowdSolver、SceneGraph，再决定复用、适配或保留当前实现。旧代码存在不等于已验证可用，但构建路径不方便也不是复制规则的理由。
- 每类运行状态只能有一个权威 owner。禁止长期同时维护两张可独立修改的角色状态表。
- 入口只做参数解析、边界校验和映射；系统调度、场景解释、玩法和导出分别归对应 owner。
- 不按行数机械拆分，不创建无明确契约的 common/utils/helpers 桶。
- 已有 `main.ts`、`renderer.ts`、`ui.ts` 不继续吸收新的玩法、会话和持久化责任。允许必要的装配接线；新增业务责任进入对应模块。

## 4. 本阶段 owner 与数据流

下列名称是责任名称，不强制要求建立同名目录。WU-0 必须将其映射到具体生产文件和测试文件。

| Owner | 责任 | 不应承担 |
|---|---|---|
| 场景数据 owner | Schema、稳定引用、校验与迁移 | GUI、GPU、僵尸行为 |
| 场景运行装载 owner | 从已验证场景解析世界变换、支持组件和来源映射，生成运行描述 | DOM、文件写入、复制另一份变换数学 |
| 僵尸游戏 owner | 玩家角色配置、房间进入、刷怪、追击及本轮移动规则 | 编辑器控件、快照文件写入 |
| Runtime 会话 owner | 实体状态、固定步推进、输入消费、查询；调用游戏系统 | 浏览器时钟采样、Inspector、资产落盘 |
| PlaySession owner | 编辑器运行会话、启停、作者快照、资源归属与清理 | 另一套追击、导航或刷怪逻辑 |
| 动态渲染 Bridge owner | 把运行实体映射到可视实例，处理身份映射与状态更新 | 静态场景持久化、独立推进模拟 |
| 编辑会话 owner | 本轮选中上下文、领域编辑命令、版本、撤销与保存 | 运行中的位置积分、复制 GUI 状态作真源 |
| CLI 与快照导出 owner | 调用共享能力、参数映射、显式导出报告 | 私自决定出生和触发规则 |

数据流：

```text
场景/资产/项目配置
        ↓ 读取、校验、迁移
共享场景运行装载 + 游戏规则装配
        ↓ 初始运行描述
Runtime 会话 ← 固定步输入序列
        ↓ 查询/可视状态
动态渲染 Bridge → GPU 画面
        └→ CLI 指标与显式快照报告

人的编辑操作 / 程序调用
        ↓ 同一套领域编辑命令
作者编辑会话 → 撤销、保存 → 下一次运行输入
```

Node 和浏览器必须共用装载与游戏规则。宿主负责把真实输入/时钟转为约定的运行输入，禁止各宿主解释一次场景语义。

## 5. 核心 contract

### 5.1 运行输入与结果

- 运行创建输入至少包含：场景及相关配置的版本标识、种子、固定步长、经过解析的运行描述。
- 玩家输入以 tick 为定位单位；按键采样在浏览器入口完成，速度与位置更新在游戏/runtime 内完成。
- 比较复现时使用相同代码与内容版本、种子、固定步长及输入序列。不要只凭 seed 宣称任意环境下位级一致；验收明确数值容差。
- Runtime 查询至少返回：会话标识、tick、实体身份、来源 NodeId、位置、朝向、当前目标和行为状态。没有目标时使用显式空值。
- 标识要能拒绝旧会话的引用；引入槽位复用时必须防止旧身份命中新实体，可评估复用已有 generation 机制。
- 现有 snapshot() 是展示数据。完整存档恢复、任意时刻倒放暂缓；本轮 Reset 可以重建初始世界，比较可以从初始状态重放。

### 5.2 固定步和生命周期

- 渲染帧率不决定游戏步数。浏览器宿主使用有上限的累加器调度，卡顿追赶策略明确；Node 直接推进规定 tick 数。
- Pause 不推进逻辑；Step 仅在暂停态推进一个固定步；Resume 不补算暂停期间的墙钟时间。
- Stop 回到进入 Play 前的作者状态，释放本会话拥有的 GPU 资源、输入监听、定时器及其他副作用。共享资产不因单个 Play 停止而被销毁。
- Play 启动失败也要走完整清理。不要在编辑器入口堆砌生命周期；不要求本轮补齐整个通用 App 调度框架。

### 5.3 场景装载

- 遵循已支持组件的 enabled 与触发语义；编辑隐藏 visible 不自动等于禁用玩法，按项目契约解释。
- 复用正式世界变换实现；不得继续只累加父节点 position。
- 玩家出生来源必须有明确持久化契约；不得依赖 rooms[0] 或节点数组顺序。现有契约不足时，先作最小 schema 扩展并补迁移与测试。
- 正式角色参数需有数据来源和校验；保留 roster 与 CharacterDef 的角色分工，不以 parseFloat 加默认常数掩盖缺失配置。
- 未支持的组件/触发类型必须给出定位到节点的 diagnostic。若它影响本轮验收，必须支持或明确阻断该运行；不能忽略后仍称为真实关卡 Play。

### 5.4 编辑与预览

- 运行实体选择能追溯到作者配置；对多个实例共用的数据，明确修改影响范围。
- 本轮作者参数在 Edit 状态修改，Play 中以检查为主。热更新运行参数、将运行状态选择性写回作者数据暂缓。
- 命令携带目标稳定身份和预期版本；过期对象或版本冲突明确失败。
- 保存失败保留未保存状态；不能把只改了内存的操作报告为已保存。
- 显式选择模拟预览不自动更改产品启动场景。新建作者场景仍按项目规则登记，已登记的历史调试快照不在本轮批量删除。

## 6. Work Unit 执行队列

每个 WU 开始前列出具体生产 owner、测试 owner、改动文件域、输入输出和失败条件。下列跨模块配合属于计划内责任；超出所声明文件域的改动先说明并取得授权。不要为形式问题反复请求已授予的范围内授权。

### WU-0：责任收敛与冻结输入

- 基于最新分支核对当前实现，不重做已完成内容。
- 为新 World 与已有 CharacterTable、CrowdSolver、SceneGraph 制作简短取舍记录：保留什么、复用什么、谁是唯一状态 owner、为何必要适配。
- 从现有 floor-1 提取验收场景需求：一个可进入战斗房间、一个尚未进入的刷怪区域、一个障碍物、明确玩家起点；实体规模保持不超过本轮 24 只的观察范围。
- 区分冻结的作者数据与已知临时模拟假设。保留作者布局和无关内容；修正“所有房间立即生成”属于预期行为变化，不能拿旧模拟站位作必须保持的基准。
- 产出后继续开发，不以完整通用框架设计为前置。

### WU-1：共享装载与最小真实关卡语义

- 从 sim-level.mjs 移出场景解释和玩法初始化；CLI 与后续浏览器调用同一入口。
- 本轮支持进入房间触发一次刷怪、组件禁用、明确玩家起点和角色配置。其他触发类型不泛化开发，但必须诊断。
- 让同一输入中的角色移动受本轮场景障碍/导航约束；优先适配现有导航能力。至少证明角色不会无视验收场景中的障碍直接穿过。
- 以新的共享入口保留原 CLI 模拟能力和显式快照导出。
- 测试 owner：场景装载测试负责变换/引用/diagnostic；房间游戏测试负责进入触发与不重复触发；移动 owner 的测试负责障碍约束。不要在多个测试文件重复认领同一 contract。

### WU-2：可控运行与身份查询

- 建立固定 tick 输入与可查询运行会话，支持从同一初始描述 Reset/重跑。
- 实体返回来源节点、目标和行为状态；数组存储位置不作为跨会话身份。
- 明确容量超限是预检查后拒绝还是受控部分生成。本阶段优先原子拒绝，错误后不留下调用者未知的半批实体。
- 测试 owner：runtime 会话测试负责步数、输入、确定性、身份有效性和失败状态；玩法测试只认领具体玩法结果。

### WU-3：实时 Bridge 与动态实例

- Bridge 直接读取 runtime 的可视状态，不循环导出/加载 .scene.json。
- 实现一份胶囊网格的最小动态批处理/instancing，动态实体不进入静态 SceneGraph 和 MAX_OBJECTS 槽位。
- 映射位置、朝向、可见/存活状态；维护 EntityId 到渲染实例的对应关系。
- 最小选择入口可先采用运行实体列表，选中后在视口高亮；不把复杂 GPU picking 作为前置，也不能只提供不可选择的动态画面。
- 保留静态关卡显示。不要为此扩展真实角色骨骼、VAT、LOD、复杂阴影等系统。
- 测试 owner：动态映射测试负责实体与实例关系；真实 GPU 探针负责可见更新、批处理路径和资源状态。

### WU-4：Play、Pause、Step、Stop

- PlaySession 接入同一个 runtime；编辑器入口只装配服务与按钮。
- 实现固定步调度、暂停/单步、Reset、Stop 及启动失败清理。
- 编辑相机与游戏相机独立。检查视角可以自由移动，不能反向改变玩家状态。
- Play 前保存作者编辑状态；本轮不要求完整通用保存系统，但 Stop 必须恢复未保存的作者状态，不能简单从磁盘重载覆盖它。
- 测试 owner：PlaySession 状态机与清理测试；浏览器集成检查负责按钮到实际运行的闭环。

### WU-5：一个可保存的局部修改闭环

- 选中运行敌人，查看来源刷怪点、当前目标与状态；Stop 后定位该来源节点。
- 默认选择已有 SpawnPoint.radius 作为本轮编辑参数，显示“生成散布半径（米）”，不要误作角色碰撞半径。使用已有 count 作为补充可选项。
- 提供领域编辑命令与最小控件，支持参数校验、撤销、保存、重开；不要求先做全组件 Inspector。
- 同种子重新运行，比较初始散布变化，其他未修改作者字段保持一致。保留 A/B 指标或关键帧，不能只展示修改后结果。
- 保存保留未消费组件和无关字段；新场景/资产改动遵循 scene:check。
- 测试 owner：对应编辑命令测试负责字段范围、撤销、冲突和持久化；端到端流程只验证上述代表性操作贯通。

### WU-6：收尾与实际业务验收

- 完成第 8 节所列业务验收，报告实测结果与未实现能力。
- 按本会话文件精确暂存；每笔规范中文 commit 立即 push，不能吞并他人工作或留下未推送提交。
- 不为了本任务重写项目记忆、清理历史目录、重构无关领域。

## 7. 本阶段失败矩阵

| 触发条件 | 所属 owner | 必须表现 |
|---|---|---|
| 场景/引用/玩家起点非法 | 场景装载 | 带路径或 NodeId 的 diagnostic；不创建半运行世界 |
| 关键组件语义未支持 | 场景装载/游戏规则 | 明确不支持；不静默执行近似规则 |
| 已进入房间重复触发 | 房间游戏 | 不重复刷同一批敌人 |
| 生成量超过容量 | 实体状态 owner | 明确失败，符合约定的原子性 |
| 暂停后继续或浏览器卡顿 | 运行调度 | 不补算暂停墙钟；追赶策略受控 |
| 旧会话实体/过期作者版本 | 查询/编辑会话 | 拒绝陈旧操作，返回当前上下文 |
| GPU 初始化/资源创建失败 | PlaySession/Bridge | 显示失败并释放本次已分配资源；作者数据保留 |
| 文件保存失败 | 编辑持久化 | 保持 dirty，显示失败，不报告保存成功 |

只有影响真实产品数据、身份、持久化、运行/渲染或本轮验收语义的问题阻断相应 WU。纯格式、非产品路径和无关文档问题进明确领域 backlog，不建立 misc/regression 兜底桶。

## 8. 最小验证与完成定义

### 必须完成的业务证明

1. Node 与浏览器使用同一初始化、seed 和固定 tick 输入，比较相同 tick 的实体身份、位置、目标/状态；使用明确容差，不只比较实体数量。
2. 玩家未进入的房间不刷怪；进入后生成一次；再次跨越边界不重复投放同一波。禁用刷怪组件不生成。
3. 本轮场景的障碍真实参与移动约束，不能把“朝玩家距离变小”当作导航正确的证据。
4. Pause 后 tick 和位置不变；Step 只增加一个 tick；不同渲染帧率不改变约定逻辑结果。
5. 选择一个敌人，能读到稳定身份、来源节点、目标和状态，并在画面中对应到它。
6. 修改一个来源刷怪点的 radius，撤销有效；保存重开保持；同输入重跑显示预期散布变化，无关作者字段不变。
7. Stop 恢复 Play 前作者状态；连续 20 次启停，受管理资源分配/释放账目平衡，监听和循环不累积，并辅助检查 GPU 内存趋势。不能只凭一次显存读数宣称无泄漏。
8. 动态实体没有消耗静态场景槽位；至少用一个超过静态物件上限的纯胶囊观察用例证明路径独立。此项只验证渲染分离，不等于 500 僵尸性能验收。

### 验证范围纪律

- 默认执行新增/受影响 owner 的定向测试及必要类型检查，不以全仓测试或全量构建替代影响分析。
- 修改 assets 后必须执行 scene:check；schema 升版补迁移测试。若公共契约改动需要扩大验证，在执行前说明受影响消费者。
- 真实 WebGPU 验证必须 headed Chrome + 硬件 GPU，禁止 headless 软件渲染充当画面证据。沿用项目固定端口、HTTPS、Tailscale 配置。
- 服务 detached 启动，记录日志与停止方式；只操作本次服务和测试 Tab，完成后关闭本次测试 Tab。
- 不重跑完整模拟导出命令来代替只读检查，因为它会写场景和项目配置。
- 现有九条测试仅证明各自断言范围；单轴位移不等于群体总速度限制，距离大于 0.05 不等于碰撞体无重叠，seed 相同不等于完整运行存档可恢复。

## 9. 最终开发报告要求

报告须包含：

1. 用户现在能完成的实际操作，以及仍暂缓的能力。
2. 主要生产 owner、唯一状态来源和责任变化；已有大文件是否增长、增长是否仅装配接线。
3. CLI 与浏览器共享的实际代码入口、输入契约和对比证据。
4. 真实场景语义支持表及 diagnostic；临时实验规则不能描述为产品行为。
5. 实际运行的最小测试、场景门禁、真实 GPU 检查；任何范围扩大及原因。
6. 作者数据前后差分、资源清理结果、已知限制。
7. 提交、逐笔推送结果与保留的他人工作区改动。

交付判断以“人能定位问题、局部修改、保存、重跑并检查结果”为准。不要以文件数量、工具数量、UI 按钮数量或测试总数替代这个闭环。
